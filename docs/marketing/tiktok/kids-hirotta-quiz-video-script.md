## 1. 1本目との違い

同じ家族写真を使うが、**話しかける相手が違う**。

| | 1本目（`red-eared-slider-family-video-script.md`） | 本動画 |
|---|---|---|
| 読み手 | 保護者 | **子ども本人** |
| 感情 | 「知らなかった、こわい」 | **「えっ、そうなの？」** |
| 中身 | 外来生物法・飼育コスト | カメの体のふしぎ（クイズ） |
| 書体 | Noto Sans CJK Bold（硬い） | **M PLUS Rounded 1c（丸ゴシック）** |
| 文字 | 漢字あり | **ひらがな中心（小1が読める）** |
| 着地 | `/kid/` | **`/kids/` カメふしぎ島** |
| 締め | 「カメライフガイド」で検索 | **「カメライフガイドで検索してね！」** |

1本目は法規制が主題なので保護者向けのままにし、本動画を子ども向けとして別に作った。
**1本の動画で両方に話しかけようとすると、どちらにも刺さらなくなる。**

## 2. 「あっ」の作り方 — 甲羅は脱げるという思い込みを壊す

アニメや絵本の影響で、多くの子どもはカメが甲羅から出られると思っている。
実際は甲羅は肋骨と背骨が変化したもので、体とつながっていて脱げない。

`assets/kids/k-01.webp`（甲羅の内側に背骨と肋骨が描かれた解剖イラスト）が
この「えっ！」を一枚で見せられる。**この画像が動画の山場。**

出題と答えは `js/kids-quiz.js` の 1 問目をそのまま使った。
動画で見た答えとサイトの答えが食い違わないようにするため。

## 5. 導線設計

- **カット3で「ミドリガメ」という名前を教える** → このアカウントは答えをくれる、と信頼させる
- **カット5で1問目の答えを出す** → クイズが成立することを見せる
- **カット7で「ぜんぶで 6もん」** → 残り5問がサイトに行く理由になる

**着いた瞬間に「さっきの画面だ」と分かる。** 動画とページが視覚的につながる。

## 7. 文字づかい

`/kids/` は全漢字にふりがなを振っている。動画では ruby が使えないため、
**ひらがなで書いた**（「外」→「そと」など）。小学1年生が音読できることを基準にしている。
カタカナは「カメ」「クイズ」「スマホ」「ミドリガメ」「ミシシッピアカミミガメ」のみ。

例外は締めの 1 文 **「カメライフガイドで検索してね！」**。
これは亀好きさんの指定文言なのでそのまま入れた。
子どもが「検索」を読めない可能性はあるので、ひらがな版
**「カメライフガイドで けんさく してね！」** に差し替えることもできる（要判断）。

## 9. CapCut での作業（BGM のみ）

1. `kame-hirotta-kids-tiktok.mp4` を読み込む（1080×1920 / 23.6 秒 / 無音）
2. BGM は**明るくテンポの速い曲**。カット点 `2.6 / 5.4 / 8.6 / 12.4 / 16.4 / 19.4` 秒にスナップ
3. **12.4 秒（答えの白フラッシュ）に曲の一番強いところを合わせる**
4. 音量 −6dB 前後、最後 1 秒フェードアウト
5. テロップ・エフェクトの追加は不要（すべて焼き込み済み）

## 11. 計測

- 遷移先: `https://kamelifeguide.com/kids/`
- bio リンクを UTM 付きにする（KPI.md「取得前の必須設定 ③」）

  ```
  https://kamelifeguide.com/kids/?utm_source=tiktok&utm_medium=social&utm_campaign=hirotta_kids_quiz
  ```

- **注意**: 締めの文言は「検索してね」なので、そこから来た人は
  GSC の指名検索になり **GA4 の `utm_source=tiktok` には計上されない**。
  この動画の効果は次の 2 つを**両方**見ないと分からない。

  | 見るもの | 取得元 | 意味 |
  |---|---|---|
  | `utm_source=tiktok` セッション | GA4 | プロフィールのリンクから来た人 |
  | 「カメライフガイド」等の指名検索の Impression / Click | GSC | 「検索してね」に反応した人 |

  指名検索が伸びていれば動画は効いている。投稿日の前後で GSC の指名クエリを比較する。

## 12. 制作メモ（同じ事故を繰り返さないために）

ffmpeg の `zoompan` は **入力フレーム 1 枚につき `d` 枚**を出力する。
静止画を `-loop 1 -t <秒>` で流し込むと入力が複数フレームになるため、
`d`×(入力枚数) 枚まで出力が膨れる。

実際に本動画の 1 カット目は **2.6 秒のはずが 169 秒**（5070 フレーム＝65×78）になっていた。
エンコード時間も同じ倍率で膨らみ、1 カットに数分かかっていた原因もこれ。

対策として `build_v2.py` では次の 2 つを入れた。

1. 出力に `-frames:v <想定フレーム数>` を指定して尺を確定させる
   （zoompan の先頭 `d` 枚が意図した動きそのものなので、切っても動きは正しい）
2. 書き出し後に `ffprobe` でフレーム数を検証し、想定と違えばビルドを止める

修正後、全体のビルド時間は 35 分見込みから **1 分**になった。
